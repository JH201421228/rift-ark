# 26. 퍼포먼스 예산

> **60fps는 기능이다.** 그리고 Capacitor WebView의 현실적 상한은 **58fps** 다 — 60이 아니라 58을 기준으로 예산을 짠다.

---

## 1. 프레임 예산

60fps = **16.67ms/프레임.** WebView 오버헤드를 감안해 **12ms를 실질 상한**으로 잡는다.

| 항목 | 예산 |
|---|---|
| 시뮬레이션 (고정 30Hz, 프레임당 0–2틱) | **≤ 2.4ms** (틱당 1.2ms) |
| 렌더 동기화 (스프라이트 위치·애니메이션) | ≤ 2.0ms |
| 트윈 · 이펙트 · 파티클 | ≤ 2.5ms |
| Phaser 드로우 | ≤ 4.0ms |
| React (10Hz에만 발생) | ≤ 1.0ms (해당 프레임만) |
| **여유** | **≥ 4.5ms** |

**여유를 남기는 이유:** GC, OS 인터럽트, WebView 컴포지터가 우리가 볼 수 없는 몫을 가져간다.

## 2. 엔티티 예산

| 항목 | 일반 | 저사양 | 절대 상한 |
|---|---|---|---|
| 동시 아군 유닛 | 40 | 28 | 60 |
| 동시 적 유닛 | 80 | 50 | 120 |
| 동시 발사체 | 60 | 30 | 128 |

## 3. 드로우콜 & 텍스처

### 3.1 드로우콜

| 목표 | 값 |
|---|---|
| 전투 씬 총 드로우콜 | **≤ 24** |
| 배경 시차 | 4 |
| 유닛 (단일 아틀라스) | 1–2 |
| 적 (세력 아틀라스) | 1–2 |
| 이펙트 | 1–2 |
| 발사체 | 1 |
| 보스 | 1 |
| UI (Phaser 측) | 2–3 |

**아틀라스 바인딩 전환이 드로우콜을 만든다.** 같은 아틀라스의 스프라이트를 연속으로 그리도록 **depth를 아틀라스 그룹 단위로 배치**한다.

> Phaser 공식 문서: *"텍스처 아틀라스를 반드시 사용하고 스왑을 최소화해야 한다."* 모바일 GPU는 단일 텍스처 바인딩 + 배치 정점에 최적화되어 있다. Phaser 3.60+ 는 iOS/Android를 감지해 **모바일 파이프라인**으로 자동 전환한다 (`autoMobilePipeline: true`).

### 3.2 텍스처 메모리

| 항목 | 값 |
|---|---|
| 아틀라스 페이지 최대 크기 | **2048 × 2048** |
| 2048² RGBA 페이지당 GPU 메모리 | **16MB** |
| 동시 상주 페이지 | **≤ 8** |
| 총 텍스처 메모리 | **≤ 150MB** (중급 안드로이드) |

**WebGL이 보장하는 `MAX_TEXTURE_SIZE` 는 2048뿐이다.** 4096은 약 99% 기기가 지원하지만 VRAM이 4배다. **2048 상한 + 멀티패킹**이 정답이다.

**해제 시점:** 보스 아틀라스는 스테이지 종료 즉시, 세력 아틀라스는 월드 전환 시 (`23` §6.3).

**티어 밖에 있는 값이 하나 있다 — `projectilePool` (2026-08-05).**
발사체 스프라이트 풀 크기이고 `quality.json` 최상위에 있다. 티어에 **넣지 않은**
이유: 몇 개가 날고 있는지는 기기가 아니라 시뮬이 정한다. 저사양에서 이 값을
줄여도 일이 줄지 않는다 — `SpritePool` 은 마르면 `grow()` 하지 않고 가장 오래된
활성분을 회수하므로, 줄이면 **날아가던 발사체가 소리 없이 사라질 뿐**이다.
티어로 줄일 수 있는 것은 이펙트·데미지 숫자처럼 "있어도 되고 없어도 되는 것"뿐이다.
값은 실측으로 정한다 (§10-B.6 · `npm run bench:pools`).

### 4.1 자동 감지

```js
// src/game/device.js — 렌더러 선택(CANVAS/AUTO)과 같은 판정을 쓴다
export function detectLowEnd(nav = globalThis.navigator) {
  if (!nav) return false;
  return (nav.hardwareConcurrency ?? 8) <= 4 || (nav.deviceMemory ?? 8) <= 2;
}
```

`qualityTier: "auto"` → `IS_LOW_END ? 'low' : 'high'`.

**판정이 두 곳에 있으면 반드시 갈라진다.** 그래서 `config.js` 는 이 값을 다시 재지
않고 `device.js` 에서 받아 재수출한다 — "Canvas 로 부팅할 만큼 낮은 기기인데 그래픽
품질은 최고"라는 상태는 아무에게도 설명할 수 없다.

**알려주지 않는 브라우저는 고사양으로 본다.** `deviceMemory` 는 사파리에 없다.
없다고 깎으면 iPhone 전량이 `low` 가 된다.

**설정에서 수동 고정 가능.** 자동 감지가 틀린 기기가 반드시 있다.

### 4.2 ⛔ 실행 중 적응(FPS 기반 상·하향)은 **없다**

이 절에는 `avgFps < 40 이면 downgrade()` 같은 코드가 적혀 있었지만 구현된 적이 없다.
만들지 않은 이유:

- 티어가 오르내리면 **그 진동 자체가** 체감 품질을 해친다. 안전하게 하려면 히스테리시스와
  안정 구간(20초)이 필요하고, 그것은 실기기에서만 조율할 수 있는 값이다 (P9-01~03).
- 지금 티어는 **네 가지 예산**만 바꾼다. 그중 `bgLayers` 는 배경을 통째로 다시 만든다 —
  전투 중 자동으로 일어나면 화면이 한 번 깜빡인다.
- 자동 감지 + 수동 고정으로 대부분이 해결된다. 남는 문제는 **측정한 뒤에** 다룬다.

되살리자고 제안하기 전에 실기기 측정치를 먼저 가져올 것.

## 5. 오브젝트 풀링

**모든 반복 생성 객체는 풀링한다.** `new Sprite()` / `destroy()` 순환이 GC 스터터의 주범이다.

```js
// src/game/pools/ProjectilePool.js
export class ProjectilePool {
  constructor(scene, atlasKey, size = 128) {
    this.scene = scene;
    this.group = scene.add.group({ classType: Phaser.GameObjects.Sprite, maxSize: size });
    // 프리워밍: 첫 발사 시 할당 스파이크 방지
    for (let i = 0; i < size; i++) {
      const s = this.group.create(0, 0, atlasKey);
      s.setActive(false).setVisible(false);
    }
    this.active = [];
  }

  fire(x, y, vx, vy, frame, damage) {
    let p = this.group.getFirstDead(false);
    if (!p) { p = this.recycleOldest(); }        // 상한 도달 시 최고령 회수
    p.setActive(true).setVisible(true).setPosition(x, y).setFrame(frame);
    p.vx = vx; p.vy = vy; p.damage = damage;
    this.active.push(p);
    return p;
  }

  release(p) {
    p.setActive(false).setVisible(false);
    // ★ 붙어 있는 모든 것을 정지시킨다 — 안 하면 보이지 않는 객체가 영원히 비용을 낸다
    this.scene.tweens.killTweensOn(p);
    if (p.trail) { p.trail.stop(); p.trail = null; }
    const i = this.active.indexOf(p);
    if (i >= 0) this.active.splice(i, 1);
  }

  // ★ active 배열만 순회한다. 128개 풀 전체를 매 프레임 도는 것은 낭비
  update(dt) {
    for (let i = this.active.length - 1; i >= 0; i--) {
      const p = this.active[i];
      p.x += p.vx * dt; p.y += p.vy * dt;
      if (p.x < 0 || p.x > 640) this.release(p);
    }
  }
}
```

**풀링 대상:** 발사체 · 이펙트 스프라이트 · 데미지 텍스트 · 유닛 스프라이트 · HP 바 · 파티클 이미터.

## 6. 충돌/타겟 탐색

**Arcade Physics를 전면 사용하지 않는다.**

| 대상 | 방식 |
|---|---|
| 유닛 ↔ 유닛 (같은 레인) | **정렬 배열 이웃 조회 — O(1)** (`22` §3.2) |
| 발사체 ↔ 적 | 같은 레인 정렬 배열의 사거리 구간 스캔 — O(k) |
| 광역 이펙트 | 레인별 x 범위 이진 탐색 |
| "도달했는가" 판정 | `Phaser.Math.Distance.Squared` (제곱 거리, `sqrt` 없음) |

레인은 1차원 문제이므로 범용 물리 엔진이 필요 없다. **더 빠르고 결정론적이다.**

Arcade Physics는 **꼭 필요한 경우에만 좁게** 쓴다. 쓸 경우 `world.overlap()` 를 `update()` 에서 직접 호출하지 말고 **등록된 Collider** 를 쓴다 (브로드페이즈가 불가능한 쌍을 제거한다).

## 7. 렌더 최적화

| 기법 | 적용 |
|---|---|
| **컬링** | 화면 밖 ±100px 스프라이트는 `setVisible(false)`. 풀에서는 회수 |
| **참조 호이스팅** | `this.physics.world`, `this.anims` 등을 매 프레임 재조회하지 않음 |
| **선택적 루프** | 풀 전체가 아니라 `active` 배열만 순회 |
| **고정 내부 해상도** | **1280×720 백버퍼가 기기와 무관하게 고정**된다 (`Scale.FIT` + 고정 width/height). 1920×1080 대비 픽셀 2.25배 적고, 무엇보다 **필레이트가 기기별로 변하지 않는다** — 921,600px × 60fps ≈ 55Mpx/s |
| **TileSprite 시차** | 타일맵 렌더 대신 4개 드로우콜 |
| **`roundPixels: true`** | 서브픽셀 렌더 제거 (픽셀아트 필수 + 성능 이득) |
| **텍스트 캐싱** | 자주 바뀌지 않는 텍스트는 `RenderTexture` 로 굽는다 |

| 항목 | 목표 | 한계 |
|---|---|---|

window.__t0 = performance.now();

// 첫 인터랙티브 프레임에서

## 9. 메모리

| 항목 | 목표 |
|---|---|
| JS 힙 (전투 중) | **≤ 120MB** |
| 텍스처 메모리 | **≤ 150MB** |
| 총 RSS (안드로이드) | **≤ 400MB** |
| **틱당 할당** | **0 목표** |

**할당 0 전략**
- `events` 배열은 `length = 0` 재사용
- 임시 객체 반환 금지 (`{x, y}` 대신 out 파라미터)
- 문자열 결합을 루프 안에서 하지 않음 (데미지 텍스트는 사전 생성 풀)
- 클로저를 매 프레임 만들지 않음

**누수 탐지:** 개발 빌드에서 씬 전환 10회 후 `performance.memory.usedJSHeapSize` 가 초기 대비 30% 이상 증가하면 콘솔 경고.

> ```
>
> 가지가 접히면 `import()` 표현식째로 사라지고, 그러면 그 모듈을 부르는 곳이
> 0곳이 되어 **청크가 아예 만들어지지 않는다.** 배포 빌드에서 이 메서드의
> 본문은 실측으로 `attachDebugOverlay(){}` 다.
>
> `check:prod` 는 이 결함을 **못 잡는다** — 오버레이 문구가 한글 UI 문구가 아니라
> ASCII 라벨이라 마커로 뽑히지 않기 때문이다. 대신 `src/game/wiring.test.js` 의
> **W4** 가 "동적 import 인가 · 정적 import 가 없는가"를 검사한다.

**씬 계약 두 가지는 그대로 지킨다** (절대규칙 3): `installViewport(this)` 와
`shutdown()`. `src/game/scenes/scenes.test.js` 가 전수 검사한다.

**오버레이는 씬 경합 정리의 예외다.** `GameManager.enforceDesiredScene()` 은
원하는 씬 하나만 남기고 전부 멈추는데, 예외 목록(`scenes/index.js:OVERLAY_SCENES`)에
`"Debug"` 가 있다 — 배포 빌드에서는 그 배열이 비어 있다.

## 10-A. ★★★ 렉의 정체는 시뮬이 아니라 **이벤트 하나당 연출 비용**이었다 (2026-08-05)

## 10-B. ★★★ 1-14 후반의 "멈춤" — 같은 범인이 아직 살아 있었다 (2026-08-05)

사용자 제보: *"**14라운드의 13번째 웨이브쯤에서 간헐적으로 게임이 멈추는 심각한

### 10-B.1 재현 — 무엇을 "멈춤"이라고 부를 것인가

**200ms 를 넘긴 프레임**을 멈춤으로 정의한다. 사람이 "끊겼다"가 아니라 "멎었다"고
말하기 시작하는 지점이고, 세면 0 이 되었는지 아닌지가 논쟁 없이 판정된다.

기준 시나리오: **1-14**, 오토 플레이, 6× CPU 스로틀(중급 스마트폰 대역), 250초.

| | 고치기 전 (첫 주행) |
|---|---|
| 프레임 최대 | **404.5ms** |

스파이크가 난 자리: **웨이브 12·13·15** — 제보의 "13번째 웨이브쯤"과 같다.

### 10-B.3 왜 §10-A 로 부족했나 — `setStyle` 이 새 병목이었다

§10-A 는 `setColor` · `setFontSize` 체이닝을 `setStyle(patch, false)` 하나로 줄였다.
캔버스 재렌더는 실제로 줄었다. 그런데 `TextStyle.setStyle` 은 **속성표 30개를

같은 페이지·같은 스로틀에서 쪼개 잰 값:

| 호출 | ms |

| 파일 | 무엇 |

### 10-B.5 실측

**연속 주행 (같은 머신 · 같은 시나리오 · 다른 것은 아무것도 돌리지 않음).**
구/신 코드를 **연달아** 한 번씩 돌린 쌍이 유일하게 공정한 비교다 —
250초짜리 주행은 머신 상태에 흔들린다.

| | 전 (Text + 트윈) | 후 (BitmapText · 트윈 0) |
|---|---|---|
| 프레임 최대 | 208.8ms | **113.1ms** |
| **200ms 초과** | **1** | **0** |
| 100ms 초과 | 2 | 1 |
| 33ms 초과 | 1,014 | **708** |
| p95 | 38.1ms | **33.9ms** |
| p99 | 51.2ms | **47.1ms** |
| fps | 49.2 | **51.9** |
| 동시 트윈 최대 | 111 | **78** |

**앞서 세 번 돌린 '전' 주행은 전부 200ms 초과 프레임을 냈다** (최대 404.5 · 268.0 ·
208.8ms · 200ms 초과 2 · 2 · 1회). **'후' 주행은 두 번 다 0 이다** (최대 113.1 · 70.0ms).

그리고 남은 스파이크의 **내용물이 달라졌다.** 웨이브 15 의 같은 자리에서:

| | 프레임 | `dmgText.show` |
|---|---|---|
| 전 | 102.5ms | **45.7ms** |
| 후 | 113.1ms | **0.0ms** |

후자의 113ms 는 **우리 JS 밖**이다 (감싼 구간 합계가 3.9ms). GC·컴포지터 몫이고,
이 티켓이 손댈 수 있는 것은 여기까지다.

### 10-B.6 풀 크기를 **실측으로** 정했다

`SpritePool.acquire()` 는 풀이 마르면 **`grow()` 하지 않는다.** 가장 오래된
활성분을 회수한다. 그래서 풀이 모자란 증상은 렉이 아니라 **침묵**이다 —
날아가던 발사체가 사라지고 엘리트 외곽선이 꺼진다. 아무 검사도 실패하지 않는다.

`npm run bench:pools` (`tools/bench-pools.mjs` · 100 스테이지 × 3 시드):

| 항목 | 실측 최댓값 | 풀 | 판정 |
|---|---|---|---|
| 동시 엔티티 | 136 (1-9) | 시뮬 엔티티 풀 256 | ✔ (`sim.test.js` 가 본다) |
| **동시 발사체** | **49** (1-13) | **80** (`quality.json:projectilePool`) | ✔ |
| 동시 데미지 숫자 | 132 (1-9) | 30 | **일부러 작다** — §2 의 화면 예산 |
| 틱당 이벤트 | 82 (1-8·1-11) | p99 예산 24 | `bench:sim` 이 본다 |

> **동시 발사체 60이 아니라 49다.** 조사 시작 시점의 가설("풀 60인데 68개가
> 날아 `grow()` 가 전투 중에 돈다")은 **재현되지 않았다.** 브라우저 실측에서
> `projPool` 활성 최대는 12 였고 `grow()` 호출은 0 이었다. 발사체는 무죄다.
>
> 다만 **발사체 풀 크기가 코드에 박혀 있던 것(60)** 은 옮겼다 —
> `quality.json:projectilePool`. **티어 안에 두지 않았다**: 몇 개가 날고 있는지는
> 기기가 아니라 시뮬이 정하고, 저사양에서 줄여도 일이 줄지 않는다(사라질 뿐이다).

## 10-C. ★★★ 멈춤이 **아무 흔적도 남기지 않던** 상태를 끝냈다 (2026-08-05)

§10-A · §10-B 로 200ms 초과 프레임을 0 으로 만든 **뒤에도** 사용자는 계속 멈춤을
겪었다. 그리고 결정적인 두 마디가 왔다: **"영원히 멈춘다"** · **"버튼조차 안 눌린다".**

그 둘이 동시에 성립하면 남는 것은 하나뿐이다 — **메인 스레드가 한 루프 안에 갇혀
있다.** 범인은 `syncProjectiles` 의 `while (pool.activeCount < list.length)` 였다
(`SpritePool.acquire()` 는 마르면 최고령을 재활용하므로 **activeCount 가 변하지
않는다**). 그 수정은 `scenes/BattleScene.js` 와 `pools/poolSizing.test.js` 에 있다.

**여기서 다루는 것은 그 버그가 아니라, 그 버그가 오래 살아남은 이유다.**

### 10-C.1 저장소에 감시 장치가 0곳이었다

| 무엇 | 그때 | 결과 |
|---|---|---|
| 전역 에러 핸들러 (`error` · `unhandledrejection`) | **0곳** | 어디서 터졌는지 아무도 모른다 |
| 씬 `update()` 보호 | **0곳** | 예외 한 번에 게임이 영구 정지 |
| WebGL 컨텍스트 손실 처리 | **0곳** | 캔버스가 조용히 얼어붙는다 |
| 프레임 지연 기록 | **0곳** | "느리다"를 숫자로 말할 방법이 없다 |

★★★ **특히 첫 두 줄이 치명적이다.** Phaser 의 rAF 루프는 이렇게 생겼다
(`dom/RequestAnimationFrame.js`):

```js
this.step = function step (time) {
    _this.callback(time);
    if (_this.isRunning) _this.timeOutID = window.requestAnimationFrame(step);
};
```

**`callback` 이 던지면 다음 프레임을 예약하는 줄에 도달하지 못한다.** `isRunning` 은
true 인 채 남고 재예약은 영영 오지 않는다 — 씬 하나의 오타, 트윈 `onComplete`,
이벤트 소비 중의 `undefined.x` **한 번**이 그대로 "게임이 멈춘다"가 된다.
그리고 **DOM 은 멀쩡하므로 HUD 버튼은 계속 눌린다.**

### 10-C.2 붙인 것

| 장치 | 파일 | 무엇을 |
|---|---|---|
| 진단 기록기 | `src/utils/diagnostics.js` | 링버퍼(미리 할당) · 종류 9가지 · localStorage 영속 |
| 전역 예외 | `src/App.jsx` | `error` · `unhandledrejection` |
| 프레임 보호 | `GameManager.installLoopGuard` | rAF 콜백을 감싼다 — **프레임 안의 모든 것**이 그 안이다 |
| 씬 보호 | `GameManager.wireUpdateGuards` | 씬 이름이 기록에 남고, 그 프레임의 렌더는 계속된다 |
| 컨텍스트 손실 | `GameManager.installContextWatch` | `webglcontextlost` · `webglcontextrestored` |
| 루프 생존 | PRE_STEP → `setLivenessProbe` | 화면은 보이는데 루프가 2초 멈추면 기록 후 `loop.wake()` |
| 프레임 지연 | `startFrameWatch` | 400ms 초과를 구간별로 기록 (rAF 콜백 하나, 할당 0) |
| **블랙박스** | `writeBeat` / `checkLastRun` | 3초마다 "살아 있음 + 상황"을 디스크에 — **무한 루프는 이것으로만 드러난다** |
| 화면 | `components/FaultOverlay` · `FaultLog` | 배너 + 설정 > 데이터 > 진단 기록 |

임계값은 전부 `src/game/data/quality.json:watchdog` 이다 (절대규칙 4).

> ★★★ **무한 루프는 페이지 안에서 관측할 수 없다.** 메인 스레드가 갇히면 rAF 도
> 타이머도 이벤트도 돌지 않는다 — "멈췄다"를 그 자리에서 적을 방법이 **없다.**
> 남는 길은 하나, **멈추기 전에 미리 적어 두는 것**이다. 감시자는 3초마다
> 심장박동(살아 있음 + 웨이브 · 엔티티 · 발사체 · 힙)을 남기고, 화면이 배경으로
> 갈 때만 '정상 종료' 표식을 세운다. 다음 실행이 표식 없는 심장박동을 발견하면
> 그것이 곧 **"지난번에 얼어붙었다"** 이고, 그때의 숫자가 그대로 재현 조건이 된다.

> ★★ **모두 배포 빌드에서 동작한다.** 사용자가 쓰는 것은 APK 이고 거기서
> `import.meta.env.DEV` 는 false 다. 개발자 도구를 열 수 없는 사람에게
> 설정 화면의 그 목록이 **유일한 창**이다.

### 10-C.3 브라우저에서 일부러 깨뜨려 확인했다

계측 장치는 아무 일도 없는 동안에는 **배선이 끊겨 있어도 정상과 구별되지 않는다.**
그래서 헤드리스 Chrome 에서 실제로 사고를 냈다 (`Emulation` · `Page.crash` CDP):

| 시험 | 결과 |
|---|---|
| 씬 `update` 에서 던지기 | 루프 **생존**(91프레임 진행) · `전투 갱신 예외 ×91` 기록 · 배너 |
| 프레임(씬 밖) 이벤트에서 던지기 | 루프 **생존** · `프레임 예외 ×30` 기록 |
| `WEBGL_lose_context.loseContext()` | `그래픽 컨텍스트 손실` 기록 · 배너 |

| **`Page.crash`** (핸들러가 하나도 못 도는 강제 종료) | 다음 실행에서 `무응답 종료 — 전투 1-14 웨이브 1 · 엔티티 12` 기록 · 배너 |

★★ 이 과정에서 **처음 배선이 실제로 끊겨 있었다**: 루프 보호를 `READY` 에서 걸었는데
Phaser 는 READY 를 emit 한 **뒤에** `loop.start()` 를 부른다 (`core/Game.js:416` → `:438`) —
감싼 콜백이 통째로 덮어써졌다. **깨뜨려 보지 않았으면 몰랐을 결함이다.**
지금은 `PRE_STEP` 에서 건다.

> 마지막 줄이 이 티켓에서 가장 중요한 숫자다. **옛 코드였다면 그 평가는 영원히
> 돌아오지 않는다.** 지금은 즉시 끝나고, 못 그린 120개가 `미표시` 로 **세어진다** —
> 조용히 사라지는 대신.

> **틱당 이벤트가 왜 게이트인가.** 시뮬 틱은 예산의 14배 여유인데 전투는 렉이
> 걸렸다 (§10-A). 틱 시간만 재면 "이벤트 하나가 렌더에 얼마나 많은 일을 시키는가"가
> 통째로 안 보인다 — 이벤트 하나가 트윈·틴트·데미지 숫자·효과음 한 벌이고,
> 프레임당 최대 8틱이 몰릴 수 있다.

**전부 하드 게이트.** 성능 회귀는 나중에 고치기가 압도적으로 비싸다.
