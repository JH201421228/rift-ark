> **이 파일은 다음 게임 프로젝트에 그대로 복사해 넣기 위한 것이다.**
> RIFT ARK 를 2026-08-01 ~ 08-06 에 함께 만들며 관찰한 것을 정리했다.
> 대상 독자는 **사람이 아니라 다음 프로젝트의 AI 에이전트**다.
>
> ⚠ 이것은 규범이 아니라 **관찰 기록**이다. 사용자가 이번엔 다르게 하겠다고 하면
> 그쪽이 맞다. 다만 아래 항목들은 **여러 번 반복해서 나타났고, 어긴 날에 실제로
> 문제가 생겼다.**

## 1. 소통

### 1.1 언어

**한국어다.** 응답 · 코드 주석 · 커밋 메시지 · 문서 전부.
영어 용어(`shutdown()`, `pointerdown`)는 그대로 쓰되 설명은 한국어로 한다.

### 1.2 요청의 형태

```
1. A 를 해줘
2. B 도 확인해줘
3. C 는 왜 이래?
```

- **번호를 붙여 여러 건을 한 번에** 보낸다
- **작업 중에도 새 번호를 추가한다** — 실제로 이번 세션에서도 네이티브 작업 중에
  문서 5종 요청이 들어왔다
- → **하던 것을 버리지 않는다.** 진행 중이던 작업을 마치고(또는 착지시키고) 새 요청으로 간다
- → **못 한 것을 조용히 넘기지 않는다.** 남긴 것이 있으면 명시적으로 말한다

### 1.3 제보의 형태 ★ 가장 중요

**추상적 개선안이 아니라 본 것을 그대로 말한다.**

| 실제 제보 | 그 안에 들어 있는 재현 조건 |
|---|---|
| "여전히 13 웨이브쯤에서 멈춰" | 특정 웨이브 · "여전히" = 이전 수정이 실패했다 |
| "색도 모두 비슷해" | 피아 식별 — 색 하나에 의존한 설계의 실패 |
| "지휘관이 너무 약하게 설계되었어" | 실측해 보니 "약함"이 아니라 "함께 자라지 않음"이었다 |
| "두 곳이 포커싱된 것처럼 보인다" | 포커스 링이 두 개 — DOM 구조 문제 |
| "우측 혹은 좌측의 네비게이션 바 때문에 버튼을 누를 수 없어" | 가로 모드 3버튼 내비 · edge-to-edge |

**대응 원칙:**

1. **그 문장을 재현 조건으로 삼는다.** 다른 상황을 상상해서 넓히지 않는다
2. **먼저 숫자로 재서 원인을 규명한다.** 증상만 덮으면 다음 턴에 같은 제보가 다시 온다
3. **제보와 실제 원인이 다르면 그 차이를 알려 준다.** "약하게 설계"가 아니라
   "함께 자라지 않음"이라는 구분이 실제로 도움이 됐다
4. 설계 문서와 충돌하면 **한 줄로 말한 뒤 그래도 요청대로 만든다**

### 1.4 UI/UX 요구의 해상도

**상호작용 수준에서 요구한다.** "좋게 만들어줘"가 아니라:

- "좌우 반반"
- "홀드했을 때 툴팁"
- "확인 모달"
- "되돌릴 수 없는 선택 앞에서는"

→ **대충 만들면 다음 턴에 다시 지적한다.** 처음부터 상호작용 수준까지 만든다.

## 2. 진행 방식

### 2.1 병렬을 원한다

> "에이전틱 코딩, 하네스, 클로드 스킬을 써서 빠르게/순식간에 진행해줘" — 여러 번 명시

요청이 3~6건씩 독립적으로 오므로 순차 처리하면 몇 시간이 걸린다.

**병렬 서브에이전트 지시서에 반드시 넣을 5가지:**

| # | 내용 | 왜 |
|---|---|---|
| ① | **소유 파일 명시** | 두 에이전트가 같은 파일을 만지면 서로 덮어쓴다 |
| ② | **건드리면 안 되는 파일 목록** | 특히 **공유 CSS 모듈**. RIFT ARK 에서는 `Meta.module.css` 를 화면 4개가 공유했다 |
| ③ | **포트 지정** | dev 서버 충돌 방지. **5173 은 사용자가 쓴다** |
| ④ | **끝나면 Chrome · dev 서버 정리** | 좀비 프로세스가 쌓인다 |
| ⑤ | **"못 한 것을 조용히 넘기지 말고 보고하라"** | 실제로 절반이 미완 항목을 남긴다 |

**스타일이 더 필요한 쪽에는** 공유 CSS 를 주지 말고 `AirMark` · `OwnedMark` 처럼
**별도 컴포넌트 + 자체 `.module.css`** 를 만들게 한다.

**착지 후:** 에이전트가 스톨하거나 중간 상태를 남길 수 있으므로
**"선언만 하고 배선 안 된 것"이 없는지 구조 검사기로 확인한다.**

### 2.2 빌드를 준다

**작업 묶음이 끝나면 요청을 기다리지 말고 실행 가능한 빌드를 뽑아 프로젝트 루트에 둔다.**

RIFT ARK 에서는:
```bash
cd FE && JAVA_HOME="C:/Program Files/Java/jdk-21.0.10" npm run build:android
cd android && JAVA_HOME="C:/Program Files/Java/jdk-21.0.10" ./gradlew assembleDebug -q
cp app/build/outputs/apk/debug/app-debug.apk ../../<프로젝트>-<날짜>.apk
```

> **환경 특성:** Windows 11 · 시스템 `JAVA_HOME` 이 JDK 21 이 아니다.
> 시스템 환경변수를 건드리지 않기로 했으므로 **빌드 명령마다 앞에 붙인다.**
> 안 붙이면 `invalid source release: 21` 로 실패한다.

**빌드 전에** lint · test · 데이터 검증 · 구조 검사 · 프로덕션 점검을 통과시킨다.
**오래 걸리는 게이트(밸런스 300시드 ≈ 2시간)는 빌드를 막지 않는다** — 배경으로 돌리고
결과가 나오면 따로 보고한다.

## 3. 검증 문화 ★ 이 사용자와 일할 때 가장 중요한 절

### 3.1 화면으로 보기 전까지 완료가 아니다

**2026-08-05 하루에 lint · 테스트 1,100+ · 검사기 셋을 전부 통과한 채로 화면에서만
드러난 결함이 셋 나왔다.**

| 결함 | 왜 자동 검증이 놓쳤나 |
|---|---|
| 두 탭이 겹쳐 보임 | `hidden` 속성은 **UA 규칙**이라 작성자 스타일의 `display:flex` 에 **진다** |
| 지휘관 HP 게이지가 통째로 사라짐 | `startBattle` 이 설정 전체가 아니라 **손으로 고른 부분집합**을 받았다. 최대치 0 · **에러 없음** |
| 이미 보유한 동료에 구매 모달이 뜸 | `disabled` 는 `click`·`mousedown` 만 막고 **`pointerdown`/`pointerup` 은 통과시킨다** |

> ★★ **세 번째는 합성 이벤트(`dispatchEvent`)로 재현되지 않는다.**
> CDP `Input.dispatchMouseEvent` 로 **진짜 입력**을 보내야 보인다.

**적용:**
1. 화면 요소를 만들거나 옮겼으면 **그 화면까지 실제로 이동**한다
2. 상태는 전역 핸들(`globalThis.__store`)로 **주입**한다
3. **폰 비율과 디자인 해상도 둘 다** 찍는다 (RIFT ARK 는 915×412 와 1280×720)
4. **되돌릴 수 없는 동작은 진짜 입력으로 눌러 본다**
5. 서브에이전트에게 시킬 때도 **이 절차를 지시서에 그대로 넣는다**

### 3.2 검사기를 만들되 검사기를 의심한다

**내가 쓴 검사기 셋이 아무것도 지키지 않는 상태로 통과한 적이 있다.**

| 실패 | 원인 |
|---|---|
| 패널 검사기 | 블록을 "다음 `pane ===` 까지"로 잘랐는데 그 블록이 **파일의 마지막**이라 범위가 파일 끝까지 늘어났다. 고친 뒤에도 **같은 탭의 조건부 블록이 두 개**라 첫 번째만 봤다 |
| 성장 곡선 검사기 | 기준선을 낮게 잡아서 **고치기 전의 잘못된 곡선도 통과**했다 |
| payload 대조 | **CRLF** 때문에 깨뜨리기 스크립트의 치환이 조용히 실패해 "통과"로 보였다 |

**적용:**
- **지키려는 코드를 일부러 되돌려 놓고 실패하는 것을 눈으로 본 뒤에만** 넣는다
- 깨뜨리기는 **백업 → 수정 → 테스트 → 복원** 순서
- **수정이 실제로 적용됐는지 개수·길이로 먼저 확인한다** (이 환경은 CRLF 다)
- 소스를 읽는 검사기는 **괄호 깊이로 정확히 자르고, "모든 일치"를 찾는다** (첫 개만 보지 않는다)
- **임계값은 데이터에서 파생시킨다** — 손으로 박은 숫자는 튜닝한 날부터 거짓말을 한다

### 3.3 이 프로젝트가 반복해서 당한 두 가지 실패 유형

다음 프로젝트에서도 같은 모양으로 나올 것이다. **처음부터 기계로 막는다.**

#### ① 같은 사실을 두 곳에 적으면 반드시 갈라진다

실제 사례:
- 같은 값이 `projectile` 과 `art.projectile` **양쪽에** 있어서, 검사기가 통과시킨 그림과
  화면에 뜬 그림이 **달랐다** (30종이 전부 같은 구체를 쏘고 있었다)
- 화면이 태그 판정을 **직접** 해서, 규칙 모듈과 답이 달랐다
- 씬이 색상 표를 데이터에서 **복사해** 코드에 박아 두었다

> **규칙: 새 값을 읽어야 하면 규칙 모듈을 경유한다. 화면이 스스로 판정하지 않는다.**

#### ② 선언했는데 아무도 읽지 않는 것

문법은 완전하고 아무도 실패하지 않는다. **기획자가 그 값을 고치며 튜닝하고 화면은
아무 반응도 하지 않는다.** RIFT ARK 에서 실제로 62/62 항목이 참조 0 이었던 필드,
발행 0·구독 0 인 이벤트가 있었다.

> **규칙: 데이터에 새 필드를 더하려면 읽는 코드를 함께 등록한다.**
> 등록 없는 필드는 검증 스크립트가 **오류로 잡는다** (선언↔소비 대조).

#### ③ HTML 속성이 대신 막아 줄 것이라고 믿지 않는다

| 속성 | 실제 |
|---|---|
| `hidden` | UA 규칙이라 작성자 스타일시트에 **진다** → **조건부 렌더**를 쓴다 |
| `disabled` | `pointerdown`/`pointerup` 은 **통과시킨다** → **콜백 첫 줄에서 규칙 모듈로 다시 거른다** |

## 4. 설계 성향

### 4.1 범위를 줄이는 결단을 한다

**2026-08-04 에 가챠 · 상점 · 배틀패스 · 광고 · 출석 · 일일/주간 퀘스트 · 방치 ·
파견 · 던전 · 탑 · 시험 · 도감 · 계측을 하루에 전부 걷어냈다.**
재화는 하나, 화면은 여섯, 성장은 세 갈래로 줄었다.

> **"있으면 좋을 것 같다"는 이유로 기능을 제안하지 않는다.**
> 절삭 목록에 있는 것을 되살리자고 제안하는 것은 사용자가 방금 되돌린 그 실수다.

**적용:** 새 기능을 제안하기 전에 **"이것이 없으면 무엇이 성립하지 않는가"** 를 먼저 답한다.
답이 "더 풍성해진다"면 제안하지 않는다.

### 4.2 원칙을 강하게 세우고 기계로 강제한다

RIFT ARK 의 "절대 규칙 10가지"는 전부 **자동 검증이 붙어 있다.**

| 원칙 | 강제 수단 |
|---|---|
| 시뮬레이션에 `Math.random()`/Phaser 금지 | ESLint 규칙 |
| 밸런스 수치 하드코딩 금지 | 데이터 스키마 검증 |
| 모든 씬에 `shutdown()` | 전수 검사 테스트 |
| 확률형 요소 금지 | 코드 리뷰 반려 사유 |
| 이모지 아이콘 금지 | 접근성 검사기 |

> **원칙을 문서에만 적으면 반드시 어긴다.** 사용자는 이것을 알고 있고, 검사기를
> 만들어 달라고 명시적으로 요구한다.

### 4.3 설계 의도를 존중하되 틀렸다고 판단하면 말한다

지휘관 건이 대표적이다. 사용자는 "약하게 설계되었다"고 봤고, 실측해 보니
**설계 문서가 4개월 동안 거짓말을 하고 있었다** (문서는 "지휘관이 맞는다"고 썼는데
지휘관을 때리는 코드가 없었다).

→ **문서와 코드가 다르면 문서가 버그라고 말하고, 코드를 문서에 맞춘다.**

## 5. 문서 성향

### 5.1 문서를 매우 중시한다

RIFT ARK 의 `docs/` 는 30개가 넘고, `CLAUDE.md` 는 **war story 축적소**다 —
"무엇이 왜 깨졌는지"가 날짜와 함께 쌓여 있다.

**적용:**
- **아키텍처 결정이 바뀌면 같은 작업에서 문서를 갱신한다**
- **깨진 것을 고쳤으면 왜 깨졌는지를 남긴다.** 고친 사실보다 원인이 중요하다
- **단일 출처를 명시한다.** "다른 문서와 이 문서가 다르면 이 문서가 맞다"

### 5.2 문서의 문체

사용자가 쓰고 좋아하는 문체가 명확하다:

- **단정적이고 짧다.** "블록은 스티키다." "탭은 언제나 다섯이다."
- **왜 그렇게 했는지가 반드시 붙는다**
- **실패담을 숨기지 않는다.** "이 문단의 마지막 줄은 4개월 동안 거짓말이었다"
- **표를 많이 쓴다**
- **`★` `★★` `⚠` `⛔` 로 중요도를 표시한다**
- **숫자를 적는다.** "실측: 42 → 0", "2-5 에서 평균 600 중 546"

> 새 문서를 쓸 때 이 문체를 따르면 사용자가 읽기 편해한다.

## 6. 하면 안 되는 것

| # | |
|---|---|
| 1 | **화면을 안 보고 "완료"라고 보고하는 것** — 테스트 통과는 완료가 아니다 |
| 2 | **깨뜨려 보지 않은 검사기를 넣는 것** |

| 6 | **작업 중 새 요청이 왔다고 하던 것을 버리는 것** |
| 7 | **못 한 것을 조용히 넘기는 것** |
| 8 | **문서 갱신을 다음으로 미루는 것** |
| 9 | **영어로 답하는 것** |
| 10 | **같은 사실을 두 곳에 적는 것** |

RIFT ARK 에서 **뒤늦게 만들어서 아팠던 것들**이다. 처음부터 만든다.

| 순서 | 무엇 | 왜 |

| 4 | **구조 검사기** — "만들었는데 아무도 못 쓰는 것"을 찾는다 | 화면 도달성 · 해금 정합 · 선언↔소비 대조 |

## 8. 이 사용자와 일할 때의 한 문장

> **"기계가 답할 수 있는 것은 전부 기계에 맡기고, 기계가 답할 수 없는 것
> ('재밌는가', '이 패배가 납득되는가')만 사용자에게 남긴다.
> 그리고 기계가 답했다고 말하기 전에, 그 기계를 한 번 깨뜨려 본다."**
