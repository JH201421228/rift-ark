## 1. S-01 — 1번 장면에 공중 적이 없다

### 증거

`capture-store-shots.mjs` 의 2026-08-07 실제 캡처 로그에서 한국어·영어, Play·iOS
후보가 모두 `airEnemies: 0` 이었다. 화면은 세 지상 레인의 교전을 보여 주지만,
`52 §3.2` 가 요구한 **공중 적 존재**는 보여 주지 못한다.

카피도 공중 전투를 직접 약속한다.

- 한국어: `세 개의 레인과 하늘. 하나도 뚫리면 안 된다`
- 영어: `Three lanes and the sky. Hold them all.`

### 촬영 전에 먼저 결정할 것

아래 둘 중 하나가 정해지기 전에는 그림 편집이나 가짜 적 주입으로 고치지 않는다.

1. 고정 장면 `#/battle/2-4` 의 실제 웨이브에 공중 적을 넣는다.
2. 공중 적이 자연스럽게 나오는 다른 실제 스테이지로 `SCENES[0]` 과 문서의 라우트를
   함께 변경한다.

캡처 전용으로 존재하지 않는 적을 합성하거나 전투 상태에 강제로 끼워 넣으면 실제
플레이 화면이라는 보장이 깨진다.

### 영향받는 파일

| 언어 | 원본 | 최종본 |
|---|---|---|
| 한국어 | `raw/play-1.png` · `raw/ios-69-1.png` | `play/play-screenshot-1.png` · `ios/ios-69-1.png` |
| 영어 | `en/raw/play-1.png` · `en/raw/ios-69-1.png` | `en/play/play-screenshot-1.png` · `en/ios/ios-69-1.png` |

### 완료 조건

- 캡처 로그의 `airEnemies >= 1`
- 세 지상 레인 중 교전 중인 레인이 3개
- 아군 하늘색 타원과 적 붉은 링을 눈으로 구분 가능
- 한국어·영어 검사기 모두 통과

## 2. S-02 — 한국어 7번 카피가 방주 화면과 맞지 않는다

현재 7번 장면의 실제 라우트는 `#/ark` 이지만 한국어 카피는 스테이지 수와 난이도를
설명한다. 영어 7번은 이미 `Rebuild the ark between runs.` 로 맞다.

한국어 단일 출처 `FE/tools/store-copy.json` 의 7번을 다음 문장으로 바꾼 뒤 다시 찍는다.

```text
출격 사이에 방주를 재건한다
```

영향받는 파일:

- `raw/play-7.png`
- `raw/ios-69-7.png`
- `play/play-screenshot-7.png`
- `ios/ios-69-7.png`

오버레이는 캡처 순간 브라우저에 얹혀 원본 PNG에 구워지므로, 카피만 바뀌어도
`compose` 만 다시 돌려서는 안 된다. **원본부터 재촬영**해야 한다.

## 3. S-03 — 광고 활성화 릴리스에서 8번을 다시 찍는다

### 현재는 왜 유효한가

`FE/src/game/data/ads.json` 의 현재 값은 `enabled: false` 이고 실제 광고 단위 ID도
비어 있다. 따라서 현재 1.0 이미지의 다음 문구는 사실이다.

- 한국어: `확률형 없음 · 광고 없음 · 인앱결제 없음 · 오프라인`
- 영어: `100 stages. No ads. No IAP. No gacha.`

### 재촬영 트리거

다음 중 하나라도 일어나면 **광고가 포함된 빌드를 스토어에 제출하기 전에** 8번을
다시 찍는다.

- `ads.json:enabled` 를 `true` 로 바꾼다.
- 실제 AdMob 광고 단위 ID를 넣고 광고 포함 릴리스를 준비한다.
- Play Console의 광고 항목을 `예`로 바꾸거나 Apple 심사 메타데이터에 광고를 신고한다.

### 교체 카피

`FE/tools/store-copy.json` 8번에서 광고 부재 주장만 제거한다.

```text
ko: 100 스테이지 · 확률형 없음 · 인앱결제 없음
en: 100 stages. No IAP. No gacha.
```

최종 문구는 광고 활성화 직전 `56 §4.1` 과 함께 다시 대조한다.

### 영향받는 파일

| 언어 | 원본 | 최종본 |
|---|---|---|
| 한국어 | `raw/play-8.png` · `raw/ios-69-8.png` | `play/play-screenshot-8.png` · `ios/ios-69-8.png` |
| 영어 | `en/raw/play-8.png` · `en/raw/ios-69-8.png` | `en/play/play-screenshot-8.png` · `en/ios/ios-69-8.png` |

광고 SDK 설치 여부만으로 즉시 재촬영하지 않는다. 사용자에게 실제로 광고가 노출되는
릴리스인지가 기준이다. 다만 `56 §8` 의 권장처럼 처음부터 광고 부재 문구를 쓰지 않기로
정책을 바꾸면 활성화 전이라도 S-03을 앞당긴다.

## 4. 재촬영 절차

### 4.1 시작 전

1. 바꿀 카피는 `FE/tools/store-copy.json` 한 곳만 수정한다.
2. 기존 원본과 최종본은 `store/_recapture-backup/<날짜>/` 로 복사해 둔다.
3. `5173` 은 사용자의 개발 서버이므로 사용하지 않는다. 캡처 도구는 `5199`, CDP는
   `9333` 을 쓴다.

### 4.2 실행

현재 도구에는 장면 하나만 찍는 `--scene` 옵션이 없다. 안전한 기본 절차는 언어별
16장을 전부 다시 찍는 것이다.

```powershell
cd FE
npm run store:capture
npm run store:compose
npm run store:check

npm run store:capture:en
npm run store:compose:en
npm run store:check:en
```

`--resume` 은 기존 원본을 그대로 유지하므로 재촬영할 번호의 원본을 백업 폴더로 옮긴
뒤에만 사용한다. 그렇지 않으면 문제 있는 원본을 성공한 것으로 보고 건너뛴다.

### 4.3 끝난 뒤

- 금지 카피를 일부러 한 번 넣어 검사기가 0이 아닌 코드로 실패하는지 확인하고 원복한다.
- Play와 iOS 결과를 각각 눈으로 본다.
- `5199` · `9333` 포트와 Chrome · Vite 프로세스가 남지 않았는지 확인한다.
- 이 문서의 해당 ID를 완료로 바꾸고 촬영일과 변경 근거를 남긴다.

## 5. 재촬영이 아닌 것

| 상황 | 필요한 작업 |
|---|---|
| App Store Connect가 2868×1320을 거부하고 2736×1260을 요구 | `en/raw`/`raw` 원본에서 `compose` 상수와 검사기 규격을 함께 바꿔 **재합성**. 게임 재촬영 불필요 |
| 피처 그래픽의 로고 위치·크기 수정 | `tools/compose-store-art.mjs` 재실행 또는 합성값 수정. 스크린샷 재촬영 불필요 |
| Play 512 아이콘 수정 | `resources/icon-512.png`와 아이콘 생성기를 먼저 고친 뒤 스토어 아이콘 재생성. 스크린샷 재촬영 불필요 |
| iPad·태블릿 지원 결정 | 기존 폰 화면의 재촬영이 아니라 새 기기 규격 세트 추가. 실기기 UI 검증이 선행 조건 |
